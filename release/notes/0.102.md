## 0.102

0.102 is a contract-cleanup release for the MCP and devrig CLI surfaces, driven by real automation built
on top of them: direct commands are discoverable, tool results are machine-parseable again, the host IDE's
identity is back in the list tools, field naming is consistent, and version numbers finally compare the
way the IDE expects.

> **Independent project.** MCP Steroid / Devrig is an independent open-source project. It is
> **not affiliated with, sponsored by, or endorsed by JetBrains.**

### devrig has one discoverable CLI

Direct MCP-tool commands now come from the same schemas devrig serves over stdio, through one Clikt
command tree ([#284](https://github.com/jonnyzzz/mcp-steroid/issues/284)). `list_projects` is canonical;
`projects` and the older `project` spelling are aliases. Root help discovers commands; focused help and
incomplete-command errors name all missing values, enum choices, and file-input alternatives, while
`devrig help <command>` provides the same route for agents that start from discovery.

Human output remains readable and can use terminal color. `--json` emits one ANSI-free document, and
generated tools share `{tool, command, isError, data}`. `devrig prompt <uri>` is the canonical resource
shortcut (the older `--uri` input remains compatible), and direct `execute_code` supports strict UTF-8
file/stdin input up to 10 MiB. `open_project --wait` returns the fresh `project_name`, `backend_name`, and
canonical path when the route appears; Maven/Gradle configuration remains a separate readiness step.

The generated commands and finite safe lifecycle routes were exercised through unit/process tests, a
stable real-IDE Docker flow, and live Claude/Codex task-first, help-first, outcome-only, and lifecycle
experiments.

### `steroid_execute_code` output is machine-parseable again

The tool result is now exactly the `execution_id:` header plus your script's own stdout — the
`[PRE] …` / `[RUN] script` / `[POST] …` stage framing and in-flight progress lines ("Waiting for
indexing to complete…") no longer interleave with the payload, so a script that prints a single
JSON document parses after stripping the first line
([#154](https://github.com/jonnyzzz/mcp-steroid/issues/154),
[#159](https://github.com/jonnyzzz/mcp-steroid/issues/159)). The progress didn't disappear: every
stage line goes to `idea.log` (with the executionId and modality profile), to MCP **progress
notifications** when your client passes a `progressToken`, and to the execution event log. Failing
pre-flight steps propagate their original error untouched, and genuine anomalies (compiler output,
a skipped post-flight sync) stay in the result as explicit content.

### The host IDE's identity is back in `list_projects` / `list_windows`

Since the 0.101 response cleanup, a client connected to a per-IDE server could no longer tell which
IDE it was talking to without a heavyweight `execute_code` call. Both list tools now carry a
`backends[]` lookup — one element per referenced backend, sorted by `backend_name`:

```json
"backends": [
  { "backend_name": "iu-47qi79c1",
    "intellij": { "name": "IntelliJ IDEA 2026.1.3", "version": "2026.1.3", "build": "IU-261.25134.95" } }
]
```

([#155](https://github.com/jonnyzzz/mcp-steroid/issues/155)). Entries keep only their
`backend_name` key (identity appears once per response, never per entry), `projects[]` are sorted
by `project_name`, and a direct in-IDE server always includes its own entry — so a fresh IDE with
zero open projects is still identifiable with one cheap tool call. **Migration:** parsers that read
the old top-level `ide.*` should switch to `backends[0].intellij` (a direct per-IDE server always
has exactly one element). The `devrig list_projects` / `devrig backend` CLI output (text and `--json`)
now lists the same identity keys in the same order as the MCP responses.

### `steroid_list_windows` uses `project_name` / `project_path`

Window and background-task entries now emit snake_case `project_name` / `project_path`, matching
the tool's own documentation, `steroid_list_projects`, and the sibling `backend_name` key on the
same entries ([#381](https://github.com/jonnyzzz/mcp-steroid/issues/381)). **Breaking:** consumers
that read the old camelCase `projectName` / `projectPath` keys must switch.

### Release and CI version numbers are finally comparable

A release used to be `0.101-<hash>` while CI builds were `0.101.<counter>-jb-<hash>` — and
IntelliJ's version comparator ordered them by whatever the abbreviated git hash happened to start
with ([#360](https://github.com/jonnyzzz/mcp-steroid/issues/360)). Starting with this release, all
lanes share one token layout, `<base>.<counter>-<lane>-<hash>`; the release lane is
`<base>.0-r-<hash>`. Within a base version the ordering is now structural — release < any CI build
< local snapshot — for every hash spelling, verified against IntelliJ's own `VersionComparatorUtil`
and pinned by tests, so update checks and custom plugin repositories can never flip direction on a
hash again.
